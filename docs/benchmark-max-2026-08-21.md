# Codex PTC v12 多模型 Max 基准报告

- 日期：2026-08-21
- 候选版本：`codex-ptc-mode/controller/runtime-v12.mjs`
- DSH：`0.1.0-rc.6`
- Node：`24.15.0`

## 结论先行

这轮测试证明了两件事：

1. **强制生成 TypeScript 并不适合所有任务。** 内置 PTC 在这条只有两个确定性读取的任务上，通常需要模型先编写 `run_code` 程序，输出 token 和等待时间都明显增加。
2. **Codex PTC 的价值是按任务形态选择工具面。** v12 对有明确文件边界的少量只读工作走原生 `read`，不生成 TypeScript；对搜索、目录扇出、命令、修改和验证链仍保留 Code Mode SDK。它不是“永远使用 PTC”，而是“只在程序编排真正有收益时使用 PTC”。

在这组单次 Max 样本里，Codex PTC 的总输入 token 比 Codex 少 **34.2%**、比 Standard 少 **43.0%**、比内置 PTC 少 **51.9%**。它的中位耗时为 **13.45 秒**，与 Codex 的 **13.54 秒**接近；平均耗时被 Sonnet 5 的 VPN/传输长尾显著拉高。严格输出成功率为 **4/5**，低于 Standard 和 Codex 的 **5/5**，失败来自 DeepSeek V4 Pro 把一个字段写成了控制器导出名，而不是请求的相对路径。

因此，v12 已经适合发布为**省输入 token 的混合工程模式**，但不应宣传为每个模型、每个任务都绝对最快。对格式必须逐字符正确的短任务，Standard/Codex 仍更稳；对混合型真实工程任务，Codex PTC 的通用工具面切换更有价值。

## 测试方法

每个“模型 × 模式”组合都新建空白会话，只运行一次，推理档位统一为 **Max**。模型名称是本次 DSH 路由显示的 endpoint 标签，结果只代表这些被测路由，不代表所有同名服务。

测试题是一条受控的跨文件只读配置追踪：

> 从一个明确给定的 preset 组合文件中读取控制器相对路径、两个控制器参数和两个压缩参数；相对 preset 目录解析控制器绝对路径；读取控制器前 60 行并核对参数；禁止 Shell、网页、计划、子代理、修改和额外检查；最后严格输出一行固定字段。

指标定义：

- **耗时**：外部 benchmark runner 的端到端 wall time，包含会话创建和组装开销，更接近用户点击发送后的等待。
- **输入 token**：该回合所有模型步骤的 `inputTokens + cacheReadTokens`。
- **输出 token**：该回合所有模型步骤的 `outputTokens`。
- **正确**：最后一行逐字符满足要求；字段值正确但引号或字段含义不符也记为失败。
- **工具**：模型直接看到并调用的工具；Code Mode 内部 SDK 子调用不重复列出。

原始结构化数据见 [`benchmarks/2026-08-21-max-vpn.json`](../benchmarks/2026-08-21-max-vpn.json)。

## VPN 对速度数据的影响

本轮全程开启 VPN/代理，因此耗时是当前网络条件下的**保守实测值**，不是模型的绝对速度。VPN 主要影响连接建立、首 token 时间、流式传输稳定性和自动重试，基本不会改变已经记入会话的输入/输出 token 数。

Sonnet 5 的 PTC 和 Codex PTC 各出现一次 `TRANSPORT` 重试，首条模型消息分别等待约 83.7 秒和 81.4 秒；Codex 虽未记录重试，首条消息也等待约 59.6 秒。这说明三条 Sonnet 长尾主要是 provider/网络路径，而不是本地工具执行——Codex PTC 的两次本地读取只用了毫秒级时间。无 VPN 的实际耗时可能更好，但需要在相同 endpoint、相同负载下重新多次运行才能给出可靠幅度。

## 从 code-only 候选到 v12

最早的 Codex PTC 候选对所有任务都走 Code Mode。它能把多个 SDK 子调用塞进一个程序，但这条简单任务仍要模型生成 TypeScript，导致输出 token 明显膨胀。v12 改为通用的任务形态选择器后，三个可直接对比的 Max 路由如下。这里统一使用 DSH 持久化日志中的 `turn/start → turn/end`，避免混用计时口径。

| 模型 | code-only 耗时 | v12 耗时 | code-only 输入 | v12 输入 | code-only 输出 | v12 输出 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPT-5.6 Sol | 52.584s | **10.403s** | 27,473 | **19,994** | 4,627 | **280** |
| Claude Opus 5 | 21.053s | **17.858s** | 60,327 | **51,026** | 2,706 | **205** |
| Claude Sonnet 5 | 114.020s | **93.594s** | 56,413 | **48,826** | 4,799 | **317** |

改进不是针对测试字段写特判，而是按任务的通用结构决定：

- 只有 1–2 个明确绝对文件路径、纯读取、无需搜索/通配符/目录扇出/命令/修改时，选择原生只读工具面。
- 需要搜索、派生路径集合、Shell、修改或验证流水线时，选择 Code Mode，仅向模型暴露 `run_code` 和生成 SDK。
- 不使用固定 `both`，避免每一步同时承担原生 schema 与 SDK 的双份上下文。
- 工具面与提示段按 agent 独立保存，避免不同会话之间泄漏上一个会话的 presentation。

真实请求头验证中，原生快路径只暴露 1 个 `read` schema；控制器提示中的工具相关固定开销从早期候选的约 3,933 token 降到约 114 token。这个数字描述的是被测请求头，不是所有 provider 的统一 tokenizer 结果。

## 为什么还要保留 PTC / `run_code`

简单读取不需要 TypeScript，但 PTC 对下面这些任务仍有明确优势：

- `read → derive → glob/grep → read → extract` 等下一步完全由上一步结果机械决定的链；
- 多文件并发读取、过滤、去重、排序、聚合，只把紧凑结果返回模型；
- 搜索后执行最小修改、运行定向测试并汇总失败的确定性流水线；
- 工具结果很大，但模型只需要少量结构化事实的任务。

v12 用 GPT-5.6 Sol Max 另跑了一条“从 `package.json` 派生测试 glob、读取第一个测试并提取测试名”的顺序依赖回归。它正确选择 Code Mode，在一个模型可见的 `run_code` 中完成，端到端约 40.30 秒，输入 25,868、输出 2,022。这个用例用于证明 Code 路径没有被原生快路径优化破坏，不用于宣称它比直接工具更快。

## 模式和模型怎么选

- **Standard**：这轮平均最快、严格输出 5/5。适合聊天、短问答和少量直接工具调用；系统工具面较大，所以输入 token 不一定最低。
- **PTC**：适合确定性依赖链和批处理，但不要把简单任务也强制变成 TypeScript。此题上输出 token 最高，不建议作为所有任务的默认模式。
- **Codex**：严格输出 5/5，工程规则完整且延迟中位数稳定。需要可预测正确性时仍是稳妥默认项。
- **Codex PTC**：输入最省，Flash/Sol 上同时最快；适合既有简单读取、又有搜索/编辑/验证链的真实工程工作。发布版仍应把严格格式失败当作模型层风险，而不是隐藏掉。

按本轮 Max 数据：Flash 和 Sol 优先 Codex PTC；Pro 的短任务优先 Standard/Codex，直到重复测试确认严格格式稳定性；Opus 若追求延迟选 Codex，若更看重输入 token 选 Codex PTC；Sonnet 这轮由网络长尾主导，不能据此判断本地模式优劣，当前短任务先选 Standard。

Max 也不是日常默认的必需条件。普通编辑和发布工作建议从模型默认档或 High 开始，只有复杂架构判断、困难调试和需要更深验证时再用 Max。

## 验证与限制

发布前验证覆盖：

- `npm test`：21/21 通过；
- task-shape 选择、原生/Code presentation、每 agent 隔离、工具 schema、控制器证据账本和零阻断 guard；
- zip 与 tar.gz 打包后分别解压安装；
- 本机 DSH `agentPreset.list` 可见且新会话能 mount `codex-ptc-mode`；
- 原生只读路径与 Code Mode 顺序依赖路径各有真实模型回归。

限制也必须保留：每个组合只有一次运行；测试期间开启 VPN；不同 endpoint 的负载、缓存和 tokenizer 不同；测试题是受控的只读任务，不能代表大型编辑、长时间调试或发布任务的全部分布。后续更可靠的报告应关闭 VPN或固定出口，每个组合至少运行 5 次，并分别报告 P50/P95、重试率和严格成功率。
