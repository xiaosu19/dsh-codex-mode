# Codex PTC v13 通用路由优化实测

- 日期：2026-08-24
- 模型：`gpt-5.6-sol`
- 推理档位：`low`
- 对比：同一 DSH、同一模型、同一题目的 `runtime-v12` 与 `runtime-v13`
- 网络：测试期间开启 VPN/代理
- 样本：每个“版本 × 任务”一次新会话，速度只作方向性比较

## 为什么修改

v12 只给路径明确的少量纯读取使用原生 `read`。任何搜索、目录扇出、命令或修改都会进入 Code Mode，因此一个小型 `glob → read` 链也需要携带完整 TypeScript SDK 并生成 `run_code` 程序。

v13 改成通用的收益路由：

- 少量读取：原生 `read`；
- 小型仓库检索：原生 `glob` / `grep` / `read`；
- 带引用的 Web 调研：直接工具调用；
- 修改、命令/测试流水线：Code Mode；
- 大范围扇出且需要统计、过滤、去重、排序或聚合：Code Mode；
- Code Mode 通过 per-agent restriction 只生成当前任务需要的 SDK，不默认携带 Web、ask-user、todo 和图片工具。

多个调用、调用并行或调用存在依赖，不再单独构成生成程序的理由。路由只使用任务形态特征，不包含 benchmark 文件名、字段名、路径或答案。

## 观察

1. 只读题正确切到三个原生搜索/读取工具，没有生成 TypeScript。首次固定上下文（system 加工具 schema）从 38,408 字符降到 14,924 字符，减少约 61.1%；总 token 减少约 53.9%。
2. 修改题仍走 Code Mode，但 SDK 从全量工具缩到文件、搜索、Shell、Job 与 Skill 核心集合。首次固定上下文从 38,407 字符降到 27,599 字符，减少约 28.1%；总 token 减少约 39.3%。
3. 修改题从 3 次 `run_code` / 18 个子调用减少到 2 次 `run_code` / 12 个子调用，独立重跑仍为 4/4 通过。
4. v13 修改题输出 token 比 v12 高 28.6%，但输入降幅更大，因此总 token 仍显著下降。输出增长来自本次模型生成差异，单次样本不足以认定为路由的稳定影响。

## 限制

- 每个组合只有一次运行，不能代替 P50/P95。
- VPN、provider 排队和缓存会影响 TTFT 与耗时；token、工具面和正确性更适合作为本轮主要证据。
- 两题覆盖跨文件读取和小型修改/验证，没有覆盖大规模聚合、Web 引用、图片任务或长上下文压缩。
- 下一轮应在固定出口下加入至少 5 次重复，并记录成功率、P50、P95、缓存命中、传输重试和 SDK 字符数。

机器可读数据见 [`benchmarks/2026-08-24-v13-sol-low-vpn.json`](../benchmarks/2026-08-24-v13-sol-low-vpn.json)。
