# Codex PTC v14 能力连续性回归报告

- 日期：2026-08-25
- DSH：`0.1.0-rc.6`
- 修复范围：外部执行任务误降级、连续工作流丢失 Code Mode、凭据文件暴露风险
- 真实模型工具面检查：`gpt-5.6-sol`，推理档位 `low`

## 日志证据

以下结论来自两条用户指出的 DSH 持久化会话日志。报告只记录工具名与脱敏后的任务形态，不包含 AK/SK、账号、业务返回值或私有路径。

| 场景 | v13 实际工具面 | 结果 |
| --- | --- | --- |
| 使用凭据查询 AWS Ohio 区域实例型号 | 首回合仅 `read`，下一回合仅 `glob` / `grep` / `read` | 先读取凭据文件，随后声称没有 AWS CLI/API 能力并要求用户切换 Code Mode |
| 已进入实施阶段后要求重新排版并补充功能 | `read` / `read_image` | 定位文件后声称无法编辑，要求再次切换模式 |
| 用户直接粘贴 AWS ValidationException | `glob` / `grep` / `read` | 能解释原因但无法修复和重新部署 |
| 候选版本已构建后回复“继续” | `glob` / `grep` / `read` | 丢失远程执行能力，之后又要求用户“开始”或重新授权执行 |

这说明问题位于 PTC presentation 路由，不是模型、权限 preset 或 AWS 本身：请求头确实只携带只读文件工具。

## 根因

1. v13 每次只根据最新一条用户文本选择工具面，没有参考上一回合仍在进行的修改、验证、恢复或部署状态。
2. AWS、云资源、远程服务器、测试/生产环境、数据库和凭据驱动查询没有独立的“需要执行能力”判定。
3. “重新排版、调整、优化、新增、添加、接入”等常见修改表达没有完整进入变更意图。
4. “测试环境”可能被命令意图中的“测试”误判，语义边界不稳定。

## v14 修复

- 外部目标与实际操作组合出现时直接选择 Code Mode，例如 AWS/服务器/测试环境加查询、获取、调用、连接、验证或部署。
- 错误、异常和失败回报默认保留可执行诊断能力；明确要求“只解释、不修改”时仍可使用低成本原生工具面。
- 路由事件读取该 agent 上一 presentation 与上一回合执行状态；“继续”“开始吧”、错误回报或图片跟进不会卸载进行中的 Code Mode。
- 扩充通用修改词，并把“测试环境/测试数据/测试账号/测试服务器”与真正的运行测试区分开。
- Code Mode 指导明确禁止要求用户启用 `exec_command`，因为 shell 已由生成 SDK 提供。
- 明确远程只读检查不需要二次确认；用户已点名部署/发布时可执行该项外部写入，不再要求重复授权。
- 凭据路径只允许在窄范围 shell/API 操作内部使用；禁止用 `read` 把 secret 字段暴露给模型或返回结果。

## 验证结果

### 确定性测试

`npm test`：29/29 通过。新增覆盖：

- 虚构 AWS/AKSK/Ohio 实例查询选择 `code-core`；
